Model assumptions and policy XML

This is a deterministic simulation, not a guarantee of live Apigee behavior. Requests follow the selected traffic profile and offset. Counters start empty. The model assumes one region / pod, one Identifier, MessageWeight=1, enabled=true and continueOnError=false. “200” means the request passes Spike Arrest; it does not predict the backend response. “429” means a policy violation; Edge Private Cloud and custom fault rules may return a different HTTP status.

Edge: Each MP enforces a minimum gap after its last accepted request. A request exactly on the boundary is accepted; rejection does not extend the gap. With UseEffectiveCount=true, the per-MP rate is rate/MP count; with false, it is the configured rate. This is a simplified smoothing model with a one-token capacity. Runtime bucket capacity, burst handling and time rounding can produce different results, especially at high rates.

X / hybrid: UseEffectiveCount=true uses an ideal sliding window shared across MPs. Accepted requests in the preceding second or minute count toward the limit; the interval is (t−window, t]. Adding MPs does not multiply this shared limit. Distributed synchronization delays are not modeled. The false option is disabled for this model.

Comparison: Fixed windows are aligned to t=0 and reset at their boundaries. Sliding windows count the most recent period. The generic token bucket starts full, refills continuously at the configured rate per period, and never exceeds its capacity; each accepted request consumes one token. Displayed wait times describe the current counter state. They are not actual Retry-After headers or a promise of acceptance despite future traffic.

Quota model scope and its relationship to Apigee
This planner is a general multi-limit model with one shared set of counters. All rules are evaluated together. By default, a request increments every counter only if it passes every rule. With “All attempts”, rejected requests increment every counter as well. Evaluation is atomic and independent of rule order.
A calendar month uses its actual length, not a 30-day sliding window. No traffic is assumed before the simulation starts. Peak recurrence is determined by the calendar day on which the peak starts.     Recommendation assumptions and Edge export compatibility
    This is descriptive sizing from supplied traffic, not a production guarantee. A suggested limit is ceil(selected complete-bucket percentile × (1 + headroom/100)), with a minimum of one. It has no awareness of backend capacity, business tiers or future growth.

    IN THIS GUIDE
    

    1. Choose the right workspace
    

    API Rate Limit Lab generates synthetic request timestamps, evaluates them against a model and explains which requests pass or fail. It runs entirely in your browser. No requests are sent to your API, no account is needed, and no simulation data is uploaded.
    

    WorkspaceUse it to answerTime scale
    Spike Arrest / AlgorithmsWhat happens at a 50 ms interval? How do MPs and UseEffectiveCount change decisions? Which algorithm allows a burst?Relative timestamps in milliseconds.
    Quotas / Peak trafficCan an API sustain daily demand under minute, hour, day and month limits? Which peak triggers the bottleneck?Calendar dates, clock times and fixed time zone offsets.
    

    These are independent experiments. The CSV advisor is a third workspace for observed traffic; see chapters 17–20. The quota planner does not automatically run the Spike Arrest policy first, and its rules do not affect the algorithm comparison. A result marked 200 means the selected checks allow the request; it does not predict a successful backend response. 429 means a simulated limit violation.
    

    Start with a small, predictable scenario. Once the behavior makes sense, add randomness and additional limits. If you want to isolate the effect of one configuration change, use a fixed seed and change one control at a time.
    


    2. Quick start: two guided workflows
    

    Inspect a single Spike Arrest decision
    1. Open Spike Arrest / Algorithms and select the 10ps / 2 MP preset.
    2. Leave Edge, UseEffectiveCount=true, round-robin routing, a 50 ms interval and 40 requests.
    3. Read the formula: each MP receives an effective rate of 5ps, so its minimum acceptance gap is 200 ms.
    4. Inspect requests #1–#5. Their results are 200, 200, 429, 429, 200. Each MP has its own acceptance timer.
    5. Click a request tile for its timestamp, MP and explanation. Use the status filter to inspect only rejections.
    6. Change UseEffectiveCount to false. Each MP now has 10ps, a 100 ms gap; all 40 requests pass under this model.
    

    Find the bottleneck in a busy week
    1. Open Quotas / Peak traffic and choose Example: busy week.
    2. The date range is September 1–8, 2026, with the end excluded. Baseline demand is 2,000 requests/day.
    3. Two daily peaks add 800 requests between 12:00–13:00 and 1,200 between 18:00–18:30. The total is 28,000 requests over seven days.
    4. Inspect the five rules: 10/second and 120/minute sliding windows; 1,000/hour, 3,000/day and 15,000/month calendar windows.
    5. Switch the seed mode to Fixed / repeatable before comparing rule changes. The displayed seed is the sample currently in use.
    6. Change one limit and press Run simulation. Compare total rejections, the first violation and each rule’s blocked count.
    

    The example button replaces the settings in its workspace. Save a scenario or plan first if you want to keep your current work.
    


    3. Spike Arrest: every control explained
    

    ControlMeaning and practical use
    

    Apigee modelEdge uses simplified per-MP smoothing. X / hybrid uses an ideal shared sliding window. Select the model that matches the behavior you want to investigate.
    

    Spike Arrest rateA positive integer. Choose ps for requests per second or pm for requests per minute. 60pm and 1ps have the same average rate but different shared-window lengths.
    

    Message Processor countThe number of MPs available for routing. It affects Edge per-MP capacity and routing. It does not multiply the shared X / hybrid limit.
    

    UseEffectiveCountFor Edge, true divides the rate by the MP count; false gives the full rate to every MP. X / hybrid forces true.
    

    Traffic profileChoose a steady interval, periodic bursts, jitter or custom timestamps. Additional controls appear only where relevant.
    

    Request intervalMilliseconds between requests for steady traffic; the mean interval for jitter; milliseconds between burst starts for periodic bursts. Zero produces simultaneous traffic.
    

    Request countTotal generated requests, including all requests across all bursts. Custom timestamps replace this field with the number of supplied values.
    

    Requests per burstHow many requests share each burst timestamp. The final burst can be smaller when the total is not an exact multiple.
    

    JitterA percentage around the interval. At 50 ms and ±50%, each generated gap is between 25 and 75 ms. Values are reproducible with a fixed seed.
    

    Custom timestampsNonnegative millisecond values separated by commas, spaces, semicolons or newlines. Values are sorted. Duplicates are retained as simultaneous requests.
    

    Start offsetAdded to every timestamp. Use it to place traffic near a fixed-window boundary without changing its spacing.
    

    MP routingRound-robin cycles through MPs; “All requests to MP 1” models concentrated traffic; seeded random routing samples an MP independently for each request.
    

    Seed mode / Seed usedVisible when traffic or routing uses randomness. Random mode draws a seed on each recalculation. Fixed mode allows manual entry and repeatable comparisons.
    

    Comparison · Bucket capacityThe starting and maximum number of tokens in the generic token bucket comparison. It does not change the main Edge or X / hybrid simulation.
    

    

    All changes in this workspace recalculate immediately. Invalid active inputs show an error and hide results until corrected. Controls hidden because they do not apply to the current traffic profile do not need to be filled in.
    


    4. How relative request timestamps are generated
    

    Request numbering starts at 1, but the formulas below use i=0 for the first request. Let S be the start offset, I the request interval and B the burst size.
    

    Steady:   time(i) = S + i × I
Burst:    time(i) = S + floor(i / B) × I
Jitter:   time(0) = S
          gap(i) = I × [1 + (2 × random(i) − 1) × jitter / 100]
Custom:   sort(input timestamps), then add S to every value
    

    For 8 requests, burst size 3, interval 100 ms and offset 50 ms, timestamps are 50, 50, 50, 150, 150, 150, 250, 250. All requests at a timestamp are processed in their displayed order.
    

    Enter decimals with a point: 0, 0.5, 1.25. Commas separate timestamps; 1,5 means two requests at 1 and 5 ms, not a request at 1.5 ms. Scientific notation is not accepted in custom timestamp lists.
    

    Jitter and random MP routing use separate deterministic random streams. Changing only MP routing therefore keeps jitter timestamps unchanged when the seed is fixed. Changing the seed, interval or traffic profile can change the arrival pattern.
    


    5. Algorithms, MP sharing and boundary behavior
    

    Edge smoothing
    With a period P of 1,000 ms for ps or 60,000 ms for pm, the minimum per-MP gap is P / rate × MP count when UseEffectiveCount is true, and P / rate when false. The first request to an MP passes. Each later request must arrive at or after that MP’s next allowed time. Rejected requests do not move that time forward.
    

    Round-robin can use multiple MPs’ independent capacity. Sending everything to MP 1 can cause rejections while other MPs receive nothing. With false, Edge’s nominal aggregate capacity is rate × MP count; compare that carefully with generic algorithms that use only one shared rate.
    

    Shared sliding window
    The model counts accepted requests in (t − P, t]. A request exactly P milliseconds old expires before the new decision. A burst can pass until the shared window contains the configured number of requests. The X / hybrid result and the generic shared sliding-window comparison use this same ideal counting model.
    

    Fixed window
    Requests belong to windows aligned to t=0: for 2ps, the windows are [0,1000), [1000,2000), and so on. The accepted counter resets at each boundary. A burst just before a boundary followed by another just after it can produce more accepted requests than a sliding window over that short interval.
    

    Generic token bucket
    The bucket starts full at the first request. Capacity is an independent setting. Tokens refill continuously at rate/P per millisecond, up to capacity; one accepted request consumes one token. Rejected requests do not consume a token. Idle time restores tokens, but never beyond capacity.
    

    These algorithms explain the model used by this tool. Real Apigee versions may use different burst capacities, rounding or distributed synchronization. The comparison table is not a list of configurable Apigee policy modes.
    


    6. Read the Spike Arrest results correctly
    

    • Total / Accepted / Rejected: counts for the complete scenario. Traffic duration is the difference between the first and last timestamp, not a request timeout or a measurement of backend throughput.
    • Formula: the effective per-MP gap or shared-window limit used for the current decisions.
    • Traffic chart: up to 40 equal time buckets. Bar height is request count. Green represents accepted requests; red represents rejections. The last timestamp is placed in the final bucket.
    • Request sequence: the first 500 requests, ordered left to right. Each tile is one request, not a time interval. Click a tile to inspect its decision.
    • Request log: the first 1,000 results matching the selected status filter. Wait is shown only for a rejection and describes the current model state.
    • MP load analysis: offered, accepted and rejected counts per MP. An unused MP can reveal routing concentration.
    • Algorithm comparison: all models receive the same generated timestamps. It reports accepted and rejected totals, acceptance percentage and the first rejection time.
    

    The Spike Arrest CSV always includes every request, even if the table is filtered or truncated. A wait of 50 ms means the current state would allow a request after that delay if no intervening traffic changes the counters; it is not an actual Retry-After response header.

    Open Quotas / Peak traffic. Each row defines an independent rule with an enabled checkbox, a request limit, a period and a window type. Use Add limit or the remove button to change the rule set. Every active rule must allow a request for it to receive 200.
    

    PeriodCalendar boundarySliding duration

    A monthly rule is a real calendar month: February can contain 28 or 29 days, and other months contain 30 or 31. It is not “30 days from the first request”. A simulation that crosses a month boundary can use both months’ separate quotas.
    

    Choose what consumes quota
    Only requests that pass every rule: a rejected request increments no counters. Evaluation is atomic; a request that passes the minute rule but fails the daily rule consumes neither. This is the default.
    All attempts: every incoming request increments every active counter, even when rejected. A sustained stream can keep a sliding quota exhausted. Counter usage may exceed its nominal limit. The request itself is also included when calculating how long an already-violated sliding rule will take to become available again.
    

    Rule order does not change the result. Disabling or removing every rule allows all generated traffic. Multiple active rows with the same period are allowed and are still checked independently.
    


    8. Set dates, time zones and baseline demand
    

    Start is inclusive and end is exclusive. September 1 at 00:00 through September 8 at 00:00 is exactly seven days; there is no request generated at the end timestamp. Dates must be between 2000 and 2099, with a maximum span of 366 days.
    

    The selected time zone is a fixed UTC offset applied to entered dates, peak times, calendar resets and displayed results. UTC+03:00 midnight corresponds to 21:00 UTC on the previous day. These are fixed offsets, not named regional time zones: daylight saving changes are not applied. The browser’s own date picker appearance can follow your operating-system locale, while the simulator’s labels and result text are English.
    

    Amount versus distribution
    Choose Total to specify exactly how many baseline requests to generate. For requests/minute, hour or day, the amount is multiplied by the full duration in that unit, then rounded down to a whole request.
    

    Baseline count = floor(amount × duration / selected unit)
Example: 100 requests/hour × 90 minutes = 150 requests
    

    Random timestamps · Uniform: the exact baseline total is independently distributed across the entire date range, at millisecond resolution. A setting of 2,000/day does not guarantee exactly 2,000 in each calendar day. Some hours and days receive more than others, and simultaneous timestamps are possible. This is an exact-total uniform sample, not a Poisson arrival process: the total count is fixed while timestamps vary.
    

    Evenly spaced: the first baseline request is at Start and the remaining requests are uniformly spaced up to, but not including, End. Peaks remain random even when the baseline is evenly spaced. Set baseline traffic to zero if you want to study peaks alone.
    

    The request estimate updates immediately. Quota results are a snapshot: after an edit, the “Configuration changed” message remains until you press Run simulation. Changing a chart grouping or a result filter does not generate new traffic.
    


    9. Schedule daily, weekly and one-off peaks
    

    A peak adds requests on top of the baseline; it does not replace baseline traffic or multiply it. Each row defines a start time, end time, additional request count and recurrence. Peak timestamps are uniformly random within their occurrence.
    

    • Every day: one occurrence on every day covered by the range.
    • Weekdays: occurrences whose start day is Monday through Friday.
    • Weekends: occurrences whose start day is Saturday or Sunday.
    • Specific date: one occurrence on the selected peak start date. A date outside the simulation range adds no traffic unless an overnight portion overlaps the range.
    

    Overnight windows
    An end time earlier than the start means the peak crosses midnight. For 23:00–01:00, a Friday weekday peak includes traffic in the first hour of Saturday. Recurrence is determined by Friday, the day the peak starts. Identical start and end times are invalid rather than meaning a 24-hour peak.
    

    Partial overlaps and rounding
    If only part of a peak falls inside the simulation, its amount is prorated by overlap duration and rounded down. A 200-request peak from 23:00–01:00 contributes 100 requests to a simulation covering only 00:00–01:00 the next day.
    

    Included peak count = floor(peak amount × overlap duration / full peak duration)
Total traffic = baseline count + sum of all included peak counts
    

    Overlapping peaks are additive. Two 12:00–13:00 rows with amounts 100 and 200 add 300 requests. Neither suppresses the other. The request log labels them Peak 1, Peak 2, and so on, based on row order in the simulated plan.
    

    Use a one-minute window to model a short surge, or several adjacent windows to approximate a changing demand curve. A peak amount of zero adds no requests. You can define up to 12 peak rows.
    


    10. Random seeds and repeatable experiments
    

    The seed is the starting value of the deterministic random generator. With identical settings and the same seed, generated traffic and simulated decisions repeat. The accepted range is an integer from 0 through 4,294,967,295.
    

    Mode or actionWhat happens
    Random per simulationThe browser draws a fresh seed. Spike Arrest does this on each recalculation when jitter or random MP routing is active; the quota planner does it when a simulation runs.
    Fixed / repeatableThe seed field becomes editable. Repeated runs keep the same seed. Use this mode to compare limits against the same traffic.
    New seedDraws a fresh seed and immediately recalculates the relevant workspace, even in Fixed mode. It keeps the selected mode.
    Switch Random to FixedKeeps the displayed seed. This freezes the current traffic sample for subsequent comparisons.
    

    Random mode is the default for new scenarios. The seed actually used stays visible; it is not an undisclosed source of randomness. For the quota planner, editing settings only updates the estimate, not the seed or results, until you run the plan.
    

    Saved snapshots deliberately use Fixed mode. Save scenario, Save plan and Download HTML include the displayed seed and set the saved copy to Fixed so it can replay that sample. The live page keeps your chosen mode. After reopening a snapshot, select Random to resume drawing new samples. Older scenario files without a seed-mode field are treated as Fixed for compatibility.
    

    The seed alone is not enough to reproduce traffic: keep every traffic setting, date, peak row and routing option as well. Changing the amount or order of peaks can change random draws for later requests. Random samples help explore variability, but a few samples are not a statistical guarantee about production traffic.
    


    11. Interpret quota results and counter usage
    

    The three summary cards count the full generated plan. Accepted requests passed every enabled rule; rejected requests failed at least one. The first rejection is displayed in the selected time zone.
    

    Traffic calendar: choose day or hour buckets. Green and red segments show accepted and rejected request counts. Long ranges combine adjacent buckets into at most 90 bars; the caption states the grouping. Hover over a bar to see its counts. Partial first or last calendar buckets contain only traffic within the simulation range.
    

    Which limit was the bottleneck? Each active rule reports its request limit, window type, number of requests it blocked, first violation and maximum observed counter usage. A single request may violate several rules, so adding blocked counts across rows can exceed the number of 429s.
    

    A zero blocked count does not mean that a rule is unnecessary. A stricter rule may reject traffic before the more generous rule fills, particularly with accepted-only counting. Disable a rule and rerun with a fixed seed to study how it affects the other counters.
    

    Request log: browse 100 rows per page, optionally filtering to 200 or 429. Each row shows a timestamp with millisecond precision, source (Baseline or Peak N), all violated limits and the earliest available time if rejected. Filtering and pagination inspect the saved run, not the edited settings.
    

    Earliest available time: the model finds when every currently violated rule would have capacity if no more traffic arrived. Calendar rules use the next reset; sliding rules wait until enough counted requests expire. When several rules block a request, the latest of their availability times is shown. Additional traffic can push acceptance later.
    


    12. Worked experiments with expected outcomes
    

    A. A 200 ms smoothing threshold
    Use Edge, 5ps, 1 MP, UseEffectiveCount=true and custom timestamps 0, 199, 200. Results are 200, 429, 200. The rejected request at 199 ms does not postpone acceptance at 200 ms.
    

    B. A burst across a window boundary
    Choose the Window boundary preset: 2ps and timestamps 998, 999, 1000, 1001. The shared sliding window accepts two and rejects two. Fixed window accepts all four because its counter resets at 1,000 ms. The comparison uses one shared rate for both.
    

    C. Burst capacity and refill
    Set 2ps, token bucket capacity 2, and custom timestamps 0, 0, 0, 499, 500. In the generic token bucket comparison, three requests pass: two at t=0 and one at t=500. Requests at 0 (the third one) and 499 ms fail. To inspect the main request log, remember that it still follows the selected Apigee model, not the token bucket comparison row.
    

    D. Two quotas blocking the same request
    In Quotas, use September 1, 2026, 00:00–00:01, baseline Total=2, Evenly spaced, no peaks, and Calendar rules of 1/minute and 1/day. The two requests arrive 30 seconds apart. The first passes; the second violates both rules. Each rule reports one violation while the total rejected count is one. The earliest available time is midnight the next day.
    

    E. A real monthly reset
    Use January 31, 2026, 23:59 through February 1, 00:01; Total=2, Evenly spaced, no peaks, and a single Calendar limit of 1/month. Requests arrive at 23:59 and 00:00. Both pass because they belong to different calendar months. If both timestamps were in January, the second would fail.
    

    F. A peak clipped at midnight
    Use September 2, 2026, 00:00–01:00, baseline=0, and a Specific date peak on September 1 from 23:00–01:00 with 200 additional requests. The estimate is exactly 100 requests. With no active rules, all 100 pass. The first half of the peak is outside the date range and is omitted.
    

    G. Separate randomness from capacity changes
    Run the busy-week plan in Random mode. Switch to Fixed without changing the seed, then run again: the same traffic is evaluated. Raise only the monthly limit and run once more. The timestamps remain unchanged, so differences in rejection counts are caused by the limit change rather than a new random sample.

    Spike Arrest exports every generated request regardless of the selected filter. Fields are request, time_ms, mp, status, wait_ms and reason. Quotas exports all rows matching its current status filter, across every page. Fields are request, time_local, utc_offset, source, status, violated_limits and next_available_local.
    

    CSV files use UTF-8 with a byte-order mark. Quota timestamps are local to the explicit UTC offset included in the file; they do not contain a trailing Z. Spike Arrest numeric timestamps use a decimal point. Explanation fields are quoted as needed. Exports always describe the last completed run; if results are marked stale, rerun first to export the edited configuration’s decisions.
    

    There is no automatic browser storage. A normal refresh of the hosted page resets unsaved edits. Download a scenario, plan or HTML snapshot before closing the page if you need to keep your work.

    15. Troubleshooting and common surprises
    

    Why do I see 429 even though average traffic is below the configured rate?
    Arrival timing matters. Edge smoothing checks gaps at each MP; bursts can exhaust a sliding window even when a longer-term average looks low. Inspect the exact request timestamps and routing.
    

    Why did the result change when I only changed a limit?
    Check Seed mode. Random mode can draw a new traffic sample during recalculation or Run simulation. Switch to Fixed to compare against identical traffic.
    

    Why does adding MPs not help in X / hybrid?
    The modeled limit is shared. MPs route the requests, but all consume one sliding-window allowance. Edge has different per-MP behavior.
    

    Why does a monthly quota reset earlier than a full month after my first request?
    Calendar windows are aligned to month boundaries. Starting on September 20 still resets at October 1, not October 20. No earlier September traffic is assumed.
    

    Why does my “2,000/day” random baseline show a different count each day?
    It becomes an exact total over the whole duration, then timestamps are distributed across that duration. It is not a per-day allocation.
    

    Why did a peak generate fewer requests than its amount?
    Its recurrence may exclude some days, it may lie partly outside the date range, or its prorated count may be rounded down. Check the start day for overnight peaks.
    

    Why is the sum of blocked counts larger than the rejected total?
    One request can violate multiple quota rules. The table attributes the request to every rule it violates.
    

    Why is the seed field read-only?
    Random mode owns the seed. Select Fixed / repeatable to type a value, or use New seed to draw another one.
    

    Why are results still showing my old plan?
    Quota edits mark the snapshot stale. Press Run simulation. Filters and chart grouping never rerun the plan.
    

    Why will my JSON file not load?
    Use the correct workspace and file kind, check version 2 versus version 3, and keep within input and file-size limits. Invalid imports leave the current configuration in place.
    

    Why is there no HTML download button in my local copy?
    That is intentional. The hosted page creates the offline snapshot without that button; the guide and other exports remain available.
    

    Can this prove my production API will return these statuses?
    No. It models policy decisions with explicit assumptions. Use controlled runtime observations for production behavior, including actual policy order and synchronization.
    


    16. Glossary, assumptions and references
    

    Rate
    Allowed requests per unit of time. Equal average rates can still behave differently when their windows differ.
    Quota
    A request allowance over a period such as a minute, day or month.
    MP
    Message Processor; the routing destination used by the Spike Arrest experiment.
    Burst / peak
    A burst in Spike Arrest is simultaneous requests. A scheduled peak in Quotas distributes additional requests across a clock-time interval.
    Seed
    A number that makes pseudorandom traffic reproducible when all other inputs are identical.
    Calendar window
    A counter period aligned to a calendar boundary in the chosen fixed time offset.
    Sliding window
    A period that looks backward from each incoming request, with older requests expiring as time advances.
    Atomic evaluation
    All active quota rules decide together before accepted-only counters are updated.
    

    The simulation starts without prior traffic. It assumes a single Identifier and unit request weight, static MP count, no retries, no network latency and no distributed synchronization delay. The quota planner uses a single shared counter set. Backend response times, queues, concurrency limits, per-user fairness and real log replay are not implemented.
    

    The generated SpikeArrest XML represents the rate and UseEffectiveCount settings only. Traffic generation, routing, seeds and generic algorithm comparisons are simulator inputs, not XML policy attributes. The quota planner does not generate a complete Apigee deployment configuration.

    18. Exclude APIs, developers, paths and other traffic
    

    Add an exclusion for an API proxy, developer, request path, developer app, HTTP status or environment. The corresponding CSV column must be mapped. Up to 20 rules are supported. Rules are combined with OR: a row matching any one rule is excluded.
    

    • Exact: exclude developer internal@example.test or API health-api.
    • Starts with: exclude every path beginning with /internal/.
    • Contains: exclude paths containing /metrics anywhere in the string.
    • Wildcard *: exclude /v1/*/health or HTTP status 5*. Only * is special; other characters are literal, not regular expressions.
    

    Matching is case-sensitive unless Ignore case is enabled. Empty patterns are invalid. With path normalization enabled, HTTP(S) URL origins, query strings and fragments are removed before both matching and grouping. For example, https://api.example.test/health?probe=1 becomes /health. Path IDs are not templated automatically: /orders/1 and /orders/2 remain different paths.
    

    The exclusion audit reports rows and request counts matched by each rule. Overlaps appear in every matching rule’s audit count, but the excluded total counts each row only once. These audit counts cover valid CSV rows before the reporting-range filter. Existing 429s and other errors are included unless you exclude them explicitly. Removing them may hide actual demand; decide which traffic population your policy should protect.
    

    Choose the enforcement scope you intend to use
    All included traffic proposes one shared allowance. Per API, developer, app or path proposes a limit for the selected group. Per API + developer uses a separate pair as the group key. The Traffic group selector shows up to the 200 busiest groups after exclusions, ranked by traffic before the date filter. Refine exclusions to reach another group.
    

    A developer-specific recommendation should not be deployed as a global limit without reconsidering its scope. The advisor does not create Identifiers or automatically push policies into Edge.
    


    19. Understand candidate limits and observed replay
    

    Confirm the reporting start and end before analysis. The initial range is based on valid CSV timestamps; request logs round outward to second boundaries, and aggregate rows extend through their bucket end. The range is an assertion of complete export coverage, not evidence that no data is missing. Adjust it to the actual export interval.
    

    For each supported calendar period, traffic is summed into second, minute, hour, day and month buckets. Only buckets fully contained in the reporting interval determine sizing. Missing buckets inside that range count as zero. A monthly recommendation needs a complete calendar month; hourly input cannot produce a second or minute recommendation. Partially included source aggregate rows are excluded entirely, without proration.
    

    Suggested limit = max(1, ceil(sizing baseline × (1 + headroom / 100)))
Sizing baseline = observed peak, P99 or P95 of complete calendar buckets
    

    Percentiles use nearest rank over all complete buckets, including zeros, and are not weighted by request count. P99 therefore does not mean “reject only 1% of requests”. A few large bursts can carry most of the traffic. In a sparse sample, P95/P99 can be zero and the candidate becomes one. The default is the observed peak plus 20% headroom.
    

    For example, complete second buckets with counts 10 and 5 have a peak of 10. With 20% headroom, the candidate is 12 requests/second. A source containing only two seconds cannot justify a minute, hourly or monthly candidate. If the report declares a full minute but only one second contains 10 requests, missing seconds count as zero; P95 is zero and a zero-headroom percentile candidate would be one.
    

    Standalone replay evaluates each proposed calendar limit independently on the observed traffic. Combined replay evaluates all supported candidates together with atomic accepted-only counters. The latter is not the sum of standalone rejections. Replay starts with empty counters at the reporting start and includes observed traffic in partial calendar periods, even though those periods do not determine percentiles.
    

    These are shared calendar-window count recommendations, not verified Edge smoothing rates. A per-second calendar allowance can accept short bursts that an Edge minimum-gap model rejects. No rate is extrapolated from coarse data, no future-demand forecast is made, and no recommendation considers backend capacity or business requirements.
    


    20. Export, clear and assess traffic analyses
    

    Download analysis JSON records the selected group, mapping, exclusions, reporting range, percentile/headroom settings, invalid-row count, recommendations and combined replay counts. Download recommendations CSV records the candidate table, including unsupported periods and their reasons. Both export the last analyzed snapshot and selected group; if settings are marked stale, analyze again first.
    

    Reports contain group names and exclusion values but no raw traffic rows. Imported data remains only in memory. Clear imported data removes it from the advisor. Download HTML deliberately restores an empty advisor in the saved copy, omitting imported CSV, filters, previews and results. The other workspaces’ settings and the complete guide remain included. Use an explicit analysis export if you want to retain the advisor result.
    

    CSV limits are 15 MB, 100,000 data rows, 100 unique non-empty headers and a maximum declared reporting span of 366 days. Aggregate totals can be up to one trillion requests without expanding them into rows. Full logs are not deduplicated automatically: identical request timestamps can represent legitimate simultaneous requests. Do not mix subtotals with their underlying rows or overlapping exports of the same population.
    

    Before acting on a candidate, check that your sample covers representative busy and quiet periods, includes the intended clients and endpoints, and is not already censored by upstream limits or missing exports. A small number of complete periods makes tail percentiles weakly supported. Increasing the date range without supplying its missing traffic creates zero buckets and can materially lower percentile recommendations.
    

    For actual Edge runtime validation, keep the proposed scope and policy semantics explicit. The advisor provides evidence from a CSV, not a deployment action or a guarantee about future 429s. See the Edge analytics metrics and dimensions reference for export fields.
