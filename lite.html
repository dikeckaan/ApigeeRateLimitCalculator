A quick guide

  1. Match your policy. Enter its rate and MP count. Under More options, check UseEffectiveCount and routing.
  2. Choose traffic speed. A 100 ms interval sends 10 requests per second. Smaller intervals send traffic faster.
  3. Read the waiting time. In this model, each MP waits after accepting a request. Arriving too early causes a rejection; rejected requests do not restart the wait.
How the model works

Minimum gap per MP = period ÷ rate × MP count when UseEffectiveCount=true. With false, the gap is period ÷ rate. The period is 1,000 ms for ps or 60,000 ms for pm.

Example: 10ps shared across 2 MPs means a 200 ms gap on each MP. With alternating routing and a 100 ms request interval, each MP receives a request every 200 ms, so all requests pass. At 50 ms, some arrive too early.

This is a simplified Edge smoothing model with one-token capacity. MPs start ready, accept at the exact boundary and do not share unused capacity. One pod, one Identifier and MessageWeight=1 are assumed. Actual runtime burst capacity and timing can differ.

200 means allowed by this model, not a guaranteed backend response. 429 represents a limit violation; Edge Private Cloud or custom fault handling may return a different HTTP status. Quotas and X/hybrid are outside this Lite model.
